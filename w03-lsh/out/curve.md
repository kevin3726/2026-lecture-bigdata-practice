## A4: 두 배 증가 시 시간 비율

| n 변화 | 전수 비교 시간 배율 | 비교 횟수 배율 |
|---|---:|---:|
| 125 → 250 | 4.38 | 4.016 |
| 250 → 500 | 4.19 | 4.008 |
| 500 → 1,000 | 4.10 | 4.004 |
| 1,000 → 2,000 | 3.70 | 4.002 |
| 2,000 → 4,000 | 5.37 | 4.001 |
| 4,000 → 8,000 | 4.23 | 4.001 |

비교 횟수는 n(n−1)/2와 일치하며 두 배 증가 시 약 네 배가 된다. 125~2,000의 시간 배율은 4.38, 4.19, 4.10, 3.70으로 대체로 제곱 증가에 맞지만, 2,000→4,000은 5.37배로 이상적인 4배보다 크다. 이를 완벽한 제곱 시간이라고 단정할 수 없으며, 백그라운드 부하·캐시·열 상태와 tracemalloc의 비용 등이 가능한 영향이다. 원인을 분리하는 추가 반복 측정은 하지 않았다.

## A2·A5: 기다리기 불편해진 크기와 메모리

4,000개에서 전수 비교가 59.23초 걸렸고, 8,000개에서는 250.66초 걸려 과제의 1분 대기 기준을 넘었다. 이번 실행에서 먼저 문제가 된 것은 메모리보다 시간이며, 메모리 고갈은 관측하지 않았다.
최대 n=8,000에서 전수 비교 peak=6,736 bytes (0.0064 MiB), LSH peak=16,417,396 bytes (15.66 MiB).
이 값은 입력 문서를 만든 후 함수 실행 중 tracemalloc으로 추적한 Python 추가 할당량이다. 입력 집합, 인터프리터와 전체 프로세스 메모리는 포함하지 않으므로 PC 전체 RAM 사용량으로 해석하면 안 된다. 전수 비교는 집합 연산의 임시 결과를 차례로 해제하지만 LSH는 서명과 역색인, 버킷을 보관한다.

## A7·A8: 교차점과 초기 비용

500개에서는 전수 비교 0.7271초 < LSH 2.3504초이고, 1,000개에서는 전수 비교 2.9798초 > LSH 2.5089초이다. 관측 교차 구간은 500~1,000개이며 측정한 크기 중 LSH가 처음 이긴 크기는 1,000개다. 구간 내부의 정확한 교차점은 측정하지 않았다.
LSH는 실제 비교 전에 역색인 구축, shingle별 120개 해시 계산, 문서별 서명 최소값 갱신, 30개 밴드 버킷 생성과 후보 중복 제거를 수행한다. 작은 n에서는 이 초기 비용이 절약한 비교 비용보다 크다. 후보가 많아지는 데이터에서는 LSH도 최악의 경우 제곱 비교가 발생할 수 있다.

## 측정 코드 보정
