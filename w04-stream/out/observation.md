# Week 4 관찰 기록

## Task 1
Bloom은 삽입 때 켠 비트를 끄지 않고 동일한 해시로 조회하므로 거짓 음성이 없다. m=8,192·k=5·n=800의 예측 거짓 양성률은 0.860%, 실측은 0.900%로 유한한 질의 표본과 해시 충돌의 변동 범위에서 가까웠다.
FM은 64개 R을 8개씩 로그 공간에서 평균해 2^평균R로 바꾼 뒤 그룹 중앙값을 취했다. 동일한 실제 distinct 19,953개에서 원시 2^R 평균은 60,064(3.010배), 중앙값은 16,384(0.821배), 그룹별 원시 평균의 중앙값은 66,944(3.355배), 선택한 방식은 18,675(0.936배)였다.
Reservoir는 i번째 항목에서 randrange(i)<k이면 해당 자리를 교체해 길이 n을 몰라도 모든 등장 위치의 최종 선택 확률 k/n을 유지한다. 스트림을 한 번만 순회하며 k개만 보관하고, FM도 64개 등록값과 최대 256개 해시 요약만 유지한다.

## Task 2
Ryzen 7 260·RAM 31.28 GiB·Windows 11·Python 3.12.14에서 Chrome·Codex/ChatGPT 등이 실행 중이었다. n=32,000,000에서 정확한 set이 92.55초로 1분 대기 기준을 넘어 중단했고 시간부터 불편해졌으며, 메모리 고갈은 관측하지 않았다.
n이 320배 늘 때 set peak는 338.82배로 O(D) 증가했고 FM peak는 1.0000배로 O(1)이었다. 최대 크기에서 set 1268.47 MiB, FM 0.703 MiB이며 이는 tracemalloc 추적 범위의 할당량으로 전체 RAM은 아니다.
FM의 추정/실제 비율은 크기에 따라 흔들려 입력이 커진다고 정확해지지 않았다. 2배 오차는 방문 규모의 대략적 판단에는 쓸 수 있지만 정확한 일일 사용자 수를 공개하거나 정산하는 경우에는 부족하며, 더 정밀한 추정기나 정확한 계산이 필요하다.

## Task 3
p≈(1−exp(−kn/m))^k에서 x=kn/m로 두면 ln p=(m/n)x ln(1−e^(−x))이고 미분값이 0인 x=ln 2에서 k*=(m/n)ln 2=6.931이므로 k=7을 선택했다. 10비트/항목의 이상적 최저치는 exp(−10(ln 2)^2)=0.8193%다.
인스턴스 40 bytes와 bytearray 9,960 bytes(헤더·seed 포함)의 지속 상태 전체가 80,000비트이며 필터용 m은 79,160비트다. 이 m의 예측은 0.8622%, 실측은 1,720/200,000=0.860%, 거짓 음성 0으로 strong 기준을 충족했지만 이상적인 0.8193% 자체에 도달한 것은 아니다; 공용 코드와 연산 중 임시 작업 공간은 지속 상태 예산과 구분했다.
n을 모르면 예상 용량과 비트 점유율을 관리하고 필요 시 오류 예산을 나눠 필터를 추가하는 scalable Bloom 방식을 고려한다. n을 너무 작게 잡으면 포화와 거짓 양성이 늘고 너무 크게 잡으면 메모리를 낭비하며, 고정 예산으로 무한한 삽입과 낮은 오류를 동시에 보장할 수 없다.
