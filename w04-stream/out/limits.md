# Task 2: 정확한 집합과 FM의 실제 메모리 곡선

측정일: 2026-10-07, 한국 시간. CPU: AMD Ryzen 7 260 w/ Radeon 780M Graphics. RAM: 33,591,296,000 bytes (31.28 GiB). Windows 11, Python 3.12.14. Chrome, Codex/ChatGPT, Windows Defender, Explorer가 실행 중이었다. 백그라운드 부하와 CPU 열 상태를 통제하지 않았으며 단일 실행 결과다.

| 스트림 항목 수 n | 실제 서로 다른 값 수 | set 시간(초) | set peak(MiB) | FM 시간(초) | FM peak(MiB) | FM 추정값 | 추정/실제 |

| 1,600,000 | 587,625 | 3.41 | 44.487 | 13.10 | 0.703 | 716,025 | 1.2185 |
| 6,400,000 | 2,349,909 | 14.09 | 179.565 | 51.11 | 0.703 | 2,493,948 | 1.0613 |
| 32,000,000 | 11,748,933 | 92.55 | 1268.468 | 320.41 | 0.703 | 14,746,338 | 1.2551 |

측정 크기는 5개이며 최대/최소 크기 비율은 320배다. 스트림은 고정 seed 246으로 span=0.4n 범위에서 n번 무작위 추출한다. 따라서 실제 distinct 수는 0.4n과 정확히 같지 않으며 이번 실측에서는 약 0.367n이었다. 두 방법은 같은 생성기를 각각 새로 실행하므로 데이터는 같지만 전체 입력은 저장하지 않는다.

## A4: 메모리 증가율을 직접 계산

| n 변화 | n 배율 | set peak 배율 | FM peak 배율 |
|---|---:|---:|---:|
| 100,000 → 400,000 | 4.00 | 2.953 | 1.000 |
| 400,000 → 1,600,000 | 4.00 | 4.024 | 1.000 |
| 1,600,000 → 6,400,000 | 4.00 | 4.036 | 1.000 |
| 6,400,000 → 32,000,000 | 5.00 | 7.064 | 1.000 |

전체 범위에서 n은 320배, set peak는 338.82배, FM peak는 1.0000배로 변했다. set은 각 distinct 문자열과 해시 테이블을 저장하므로 대체로 distinct 수에 비례하는 O(D) 공간이다. Python set의 테이블 크기 조정과 문자열 길이 때문에 각 구간의 비율이 n 배율과 완전히 같지는 않다. FM은 64개 등록값과 고정 크기 배치만 보관하므로 n에 대한 공간 증가율은 O(1)이다. 해시 수나 배치 크기를 바꾸면 상수 메모리는 바뀐다.

## A2: 불편해진 크기와 중단 이유

n=32,000,000에서 정확한 set 방식은 92.55초, peak 1268.47 MiB를 사용했다. 이번 과제에서는 정확한 방법이 1분 이상 걸리는 것을 시간상 불편한 기준으로 삼았고, 이 크기에서 해당 기준을 넘어서 측정을 중단했다. 메모리 부족이나 시스템 전체 RAM 고갈은 관측하지 않았으므로 이 크기를 “정확한 계산이 불가능한 최대 크기”로 주장하지 않는다.
같은 크기의 FM 시간은 320.41초였다. FM의 장점은 고정 공간이며, 이번 64개 해시 구현에서 속도 향상을 보여준 것은 아니다. SHAKE-256 해시 계산과 등록값 갱신 비용 때문에 set보다 느렸다.

## A5: 정확도는 크기가 커질수록 좋아지는가?

표의 추정/실제 비율에서 1이 정확한 추정이고, 0.5–2.0은 과제 허용 범위다. 이 실측값들은 크기에 따라 변하며 단조롭게 좋아지거나 나빠지지 않는다. 해시 수를 고정한 채 n만 늘려도 상대 오차가 자동으로 사라지지 않는다. 한 가지 seed의 결과이므로 모든 데이터와 seed에서 2배 이내라고 보장할 수 없다. 전체 방문 규모를 거칠게 파악하는 데는 유용하지만 과금·정산·정확한 이용자 통계에는 부족하다.

## 측정 범위와 재현 방법

시간은 생성기에서 항목을 만드는 비용과 알고리즘 처리 비용을 함께 포함한다. 두 방법 모두 생성 비용을 포함하며, tracemalloc 추적 오버헤드도 포함한다. 메모리는 함수 실행 동안 추적한 할당량의 peak이며 전체 PC RAM이나 전체 프로세스 메모리는 아니다. NumPy 2.3.5는 측정 전에 import되어 모듈 로딩 메모리는 포함하지 않는다. NumPy 등 외부 라이브러리의 모든 내부 할당까지 포괄한다고 보장하지 않는다.
FM은 NumPy로 최대 256개의 해시 요약을 묶어 뒤쪽 0 수를 계산한다. 원본 스트림을 보관하거나 재순회하지 않고 고정 크기 작업 공간을 사용한다. NumPy가 없으면 같은 계산을 기본 Python으로 수행한다. 두 경로의 추정값 일치를 검사했지만 시간·메모리는 다른 경로에서 재측정해야 한다.

```text
python task2_limits.py --sizes 100000,400000,1600000,6400000
python task2_limits.py --sizes 32000000
```

limits.json에는 실행 결과가 추가된다. 다른 실행과 비교할 때 크기뿐 아니라 실행 환경, 해시 수, 가속 경로도 같았는지 확인해야 한다.
